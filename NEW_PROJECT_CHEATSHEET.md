# Шпаргалка: начало нового проекта

## Сразу после создания проекта

- [x] Создать `AGENTS.md` с инструкциями для агента.
- [x] Создать `PREFERENCES.md` и указать в `AGENTS.md`, что перед каждой работой агент обязан прочитать предпочтения и строго им следовать. В предпочтениях закрепить правила: постоянно поддерживать Obsidian-хранилище и сохранять в нём `CHANGELOG.md`, `README.md` и `STRUCTURED_IDEAS.md`; никогда не включать личные или конфиденциальные сведения в публичные, локальные или демонстрационные ссылки.
- [x] При создании сайта создать в корне репозитория `LINKS.md` и включить в него полный реестр ссылок сайта. Правило о ведении и обновлении этого файла обязательно добавить в `PREFERENCES.md` сайта.
- [x] Создать `BUGS.md` для фиксации ошибок и записать в предпочтениях правило никогда его не изменять.
- [x] Создать Obsidian-хранилище с папкой `.obsidian/`.
- [x] Добавить в хранилище `CHANGELOG.md` и `PROJECT.md`.
- [x] Записать в предпочтениях обязанность обновлять changelog и описание проекта при разработке.
- [x] Создать `HANDWRITTEN_IDEAS.md` для ручных идей пользователя и запретить агенту его редактировать.
- [x] Создать `STRUCTURED_IDEAS.md`: агент обновляет его на основе `HANDWRITTEN_IDEAS.md`, сохраняя оригинальные заметки нетронутыми.

## Правило работы с идеями

1. Пользователь вносит мысли в `HANDWRITTEN_IDEAS.md` в любом удобном виде.
2. Агент читает их, но не меняет этот файл.
3. Агент переносит понятные задачи, вопросы и приоритеты в `STRUCTURED_IDEAS.md`.
4. Выполненные изменения фиксируются в Obsidian: в `CHANGELOG.md` и, если нужно, в `PROJECT.md`.

## Правило хранения документации

Obsidian — основное место для проектной документации. Агент поддерживает актуальность `CHANGELOG.md`, `README.md` и `STRUCTURED_IDEAS.md` именно в Obsidian-хранилище, согласно `PREFERENCES.md`.

## Язык проекта

- Весь проект ведётся на русском языке: документация, тексты интерфейса, комментарии, сообщения, записи в журнале изменений и рабочие заметки.
- Имена файлов, команды, API, технические ключи и код остаются без перевода, если перевод нарушает работу проекта или требования используемой технологии.
- Это правило добавляется в `AGENTS.md` и `PREFERENCES.md` каждого нового проекта.

## Безопасность ссылок и адресов

1. В публичных, локальных, демонстрационных и документируемых URL запрещены личные или конфиденциальные данные: ФИО, никнеймы, связанные с человеком, адреса электронной почты, телефоны, домашние адреса, личные идентификаторы учётных записей, рабочие пространства и пути профиля пользователя. Допустимы нейтральные названия проекта и публичного бренда, не раскрывающие человека.
2. Для адресов сайта, репозитория, маршрутов и локального запуска используются только нейтральные имена проекта. Допустимые локальные примеры: `http://localhost:4173` и `http://127.0.0.1:4173`; запрещены ссылки вида `file:///C:/Users/<имя>/...`.
3. Перед каждым коммитом и деплоем агент обязан проверить изменённые файлы, документацию, конфигурацию хостинга и выданные ссылки на отсутствие таких данных. Если безопасный домен недоступен, не публиковать и не документировать адрес с личным идентификатором.
4. Это правило обязательно добавляется в `PREFERENCES.md` каждого нового проекта и применяется к README, журналу изменений, Obsidian-документации, примерам команд и ссылкам в интерфейсе.

## Полный реестр ссылок сайта

1. Для каждого создаваемого сайта в корне Git-репозитория создаётся и отслеживается файл `LINKS.md`. Он является единым реестром всех адресов, относящихся к сайту.
2. В `LINKS.md` указываются фактические адреса главной страницы и всех публичных алиасов, репозитория, внешних переходов, страниц и маршрутов, навигационных якорей, ссылок в кнопках и подвале, форм и клиентских запросов к API. Для API записываются HTTP-метод и необходимость авторизации.
3. Для каждой записи нужны понятное название, точный адрес, назначение и ограничения доступа. Не выдумывать отсутствующие домены и адреса: пока адрес не создан, указывать его отсутствие текстом, а не подставлять пример или догадку.
4. При добавлении, изменении или удалении любой ссылки агент одновременно обновляет `LINKS.md`. Перед коммитом он сверяет реестр с `href`, `action`, маршрутизацией и клиентскими запросами в коде, проверяет безопасность адресов и добавляет сам реестр в тот же Git-коммит.

## Обязательная итоговая проверка

1. После завершения каждой задачи, перед коммитом, деплоем или передачей результата агент выполняет отдельную полную итоговую проверку. Она не заменяется проверкой отдельных изменённых строк.
2. Полная проверка включает: просмотр относящихся к задаче изменений и `git status`; релевантные сборку, тесты и статический анализ; актуальность документации и `LINKS.md` для сайта; проверку изменённых публичных, локальных и демонстрационных ссылок на безопасность. Для интерфейса обязательны визуальная проверка и проверка основных сценариев взаимодействия на целевой платформе или в ближайшем доступном эквиваленте.
3. Если проверка выявила любую проблему — в коде, UI, документации, сборке, тестах, конфигурации или безопасности, — агент устраняет её в рамках задачи и затем повторяет весь цикл итоговой проверки с начала. Повторять цикл нужно до тех пор, пока очередная полная проверка не завершится без проблем.
4. Только после чистой полной проверки агент создаёт коммит из относящихся к задаче файлов и отправляет его в настроенный удалённый репозиторий. Чужие и не относящиеся к задаче изменения не добавляются в коммит.
5. Это правило обязательно переносится в `PREFERENCES.md` и `AGENTS.md` каждого нового проекта.
